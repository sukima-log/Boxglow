## 1. 要件の整理

### 1.1 アプリの目的

- タスク (目標) を「入力 -> 処理 (ブロック) -> 出力」の形で定義し、ブロック図として可視化する
- 大きな目標を、下の階層のブロック図に分解していくことで、曖昧な考えを具体化する
- どのブロックが完了していて、誰が担当しているかを一目で分かるようにする
- SW 開発のように「細かな部品を組み合わせて大きなものを作る」作業に向ける
- Codex / Claude Code / ChatGPT / Copilot / Gemini などの AI に作業を頼むとき、人間の考えを整理して渡す土台にする

### 1.2 機能要件

| 番号 | 分類 | 要件 | 優先度 |
|---|---|---|---|
| F-01 | ブロック | ブロックを作成できる。作成直後の状態は BlackBox | 必須 |
| F-02 | ブロック | 入力ポートと出力ポートを持つ。出力は必須、入力は任意 (後から追加できる) | 必須 |
| F-03 | 階層 | ブロックの中に下の階層のブロック図を作れる (再帰的に分解できる) | 必須 |
| F-04 | 結線 | 出力は、上の階層の出力・同じ階層の別ブロックの入力につなげられる | 必須 |
| F-05 | 結線 | 入力は、上の階層の入力・同じ階層のブロックの出力につなげられる | 必須 |
| F-06 | 結線 | 下の階層で未接続の入力は、自動で最上位の入力ノードまで伸びる。途中に変換ブロックを挟んでつなぎ直せる | 必須 |
| F-07 | 階層 | 階層の折りたたみ / 展開ができる | 必須 |
| F-08 | 状態 | Black -> Gray -> White の 3 段階。完了 / 未完了が一目で分かる | 必須 |
| F-09 | 担当 | ブロックに担当者を割り当て、誰が担当か分かる | 必須 |
| F-10 | 配置 | ブロックはドラッグで自由に移動できる | 必須 |
| F-11 | 結線 | 入出力の結合をドラッグで自由に行える。最終出力ノードは複数入力を持てる | 必須 |
| F-12 | 成果物 | 入力ノード・中間ブロックに成果物 (URL など) を紐づけられる | 必須 |
| F-13 | 保存 | JSON で書き出し・読み込みができる | 必須 |
| F-14 | UI | モダンで見やすい。ダークモード / ライトモード切替 | 必須 |
| F-15 | 表示 | 記事の枠内ではなく、画面いっぱいに表示する | 必須 |
| F-16 | 共同 | 複数人で作業できる (順番に編集して保存。招待制) | 高 |
| F-17 | AI 連携 | AI にタスクを渡しやすい形 (テキスト) で出力できる | 高 |
| F-18 | 連携 | Redmine など主要タスク管理ツールと組み合わせられる | 将来 |
| F-19 | 公開 | タスクを世界に公開し、見ず知らずの人が 1 ブロックずつ解決・具体化できる | 将来 |

## 2. 実現方針

### 2.1 配置

| 段階 | アプリ本体 | バックエンド | 入口 |
|---|---|---|---|
| 1 (1 人用) | **www.sukimalog.com/apps/<名前>/** (ファイル置き場。File Manager API で配置) | なし (ブラウザ内保存 + JSON 書き出し) | 紹介記事 (livedoor) |
| 2 (招待制) | **app.sukimalog.com** (Cloudflare Pages。お名前.com に CNAME 1 件) | Pages Functions (Workers) + D1 + R2 | 同上。旧 URL `/apps/<名前>/` には転送用の HTML を残す |
| 3 (世界公開) | 同上 | 同上 + Turnstile 等 | 同上 + アプリ自身の公開プロジェクト一覧ページ |

段階 2 でアプリを Pages に移す理由
- 認証 (Cookie) とデータ保存の API を **同じオリジン** に置けるので、サードパーティ Cookie の制約を受けない
  (livedoor に本体を置いたまま API だけ Cloudflare にすると、別オリジンになりトークン管理が面倒になる)
- 段階 1 のうちからビルドの `base` パスを設定で切り替えられるようにしておき、移設はビルド設定の変更と転送用 HTML の設置だけで済ませる
- お名前.com 側の DNS 作業: `app` の CNAME を `<プロジェクト名>.pages.dev` に向ける (サブドメインなら Cloudflare にゾーンを移す必要はない)

### 2.2 認証と公開範囲 (段階 2 以降)

- 招待制と世界公開の両方が要るため、Cloudflare Access (社内向けの仕組み) ではなく、**アプリ自身のログイン (Google / GitHub の OAuth)** を最初から採用する
- プロジェクトの公開範囲は 3 種類: `private` (メンバーのみ) / `link` (URL を知っていれば閲覧可) / `public` (一覧に載り誰でも閲覧・提案可)
- 権限: owner / editor / viewer。招待はメールまたは招待リンク
- 「順番に編集」の実装: 保存時に版番号 (version) を比較する楽観ロック + 「編集中: <誰>」の表示 (10 分で自動解除の軽いロック)。
  衝突したら両方の内容を見せて選ばせる

### 2.3 状態 (Black / Gray / White) の見せ方

色相で分けず、**「ボックス」の見た目**で区別する。ダーク / ライトどちらでも破綻しない。

| 状態 | 意味 | 見た目 |
|---|---|---|
| BlackBox | 出力は決めたが中身は未定 | 濃い塗り + 破線の枠 + 「?」の印。ラベル「BLACK」 |
| GrayBox | 分解中 / 着手中 | 斜線 (ハッチ) の塗り + 進捗バー (下の階層の White 率)。ラベル「GRAY」 |
| WhiteBox | 入力から出力が得られることが確定 (完了) | 明るい塗り + 実線の枠 + チェック印。ラベル「WHITE」 |

- 色 (アクセント) は担当者のアバターと選択状態だけに使い、状態には使わない
- 親ブロックを畳んだときは、中身の White 率を進捗リングで表示する。全体の完了率はフッターに常時表示
- 画面全体が「黒いボックスが白くなっていく」様子として見えるのが、このアプリの一番の見どころなので、
  状態の変化にはアニメーション (ボックスの蓋が開く / 明るくなる) を付ける

### 2.4 名前の候補 (英語で伝わる一語。Redmine のような造語)

条件: 「黒いボックスが白くなって成果物ができあがる」ことが伝わる。英語圏でも読める。既存の製品名と重ならない。

| 候補 | 読み | 由来 | 既存製品との重なり (2026-10-01 検索) |
|---|---|---|---|
| **Boxglow** | ボックスグロウ | ボックスが光る = 中身が見えて完了に近づく。状態変化のアニメーション (ボックスが明るくなる) と一致 | 見当たらない |
| Knownbox | ノウンボックス | Blackbox (unknown) を known にしていく | 見当たらない |
| Boxlit | ボックスリット | ボックスに明かりが灯る | 「BOX LITE」「Boxlight (教育機器)」と紛れやすい |
| Clearbox / Boxclear | クリアボックス | ボックスが透けて見える | 同名の企業・アプリが多数あり不可 |
| Whitebox | ホワイトボックス | 状態名そのもの | 一般用語 (whitebox testing) で検索に埋もれる |

決定 (2026-10-01): Boxglow。URL は https://www.sukimalog.com/apps/boxglow/、リポジトリは ~/src/boxglow。

### 2.5 技術スタック

| 層 | 選定 | 理由 |
|---|---|---|
| UI | React + TypeScript + Vite | React Flow が React 前提。型でデータモデルの崩れを防ぐ |
| ノード図 | React Flow (@xyflow/react) | ドラッグ・結線・親子ノード・ミニマップが揃っている |
| 状態管理 | Zustand (単一の JSON ドキュメント) | 同時編集が不要になったので Yjs は使わない。保存は JSON 1 つ + 版番号 |
| 保存 (段階 1) | IndexedDB (自動保存) + JSON 書き出し / 読み込み | |
| 保存 (段階 2) | Cloudflare D1 (プロジェクト・メンバー・版) + R2 (JSON のスナップショット・添付) | |
| API | Hono (Pages Functions / Workers) | 軽量。OAuth ライブラリ (arctic 等) と組み合わせやすい |
| スタイル | Tailwind CSS + 自前コンポーネント | ダーク / ライトのトークン管理が楽。配色は sukima pop (templates/theme/DESIGN.md) を流用 |
| 書き出し | JSON (schema_version 付き) / Markdown (AI 用) / Mermaid (図の共有用) | F-13, F-17 |
| テスト | Vitest (結線ルール・循環検出・自動引き上げの純粋関数) + Playwright (主要操作) | |
| 配置 (段階 1) | File Manager API で `/apps/<名前>/` に置く配置スクリプト (scripts/theme.py と同じ作り) | |

## 3. アプリの設計

### 3.1 データモデル

```
Project
  id, name, description, created_at, updated_at, schema_version, version (楽観ロック用)
  visibility          : "private" | "link" | "public"
  members[]           : { user_id, name, color, role: "owner" | "editor" | "viewer" }
  blocks[], ports[], edges[], artifacts[]

Block (ブロック = タスク)
  id
  parent_id           : null なら最上位
  title, description
  status              : "black" | "gray" | "white"
  assignee_ids[]      : 担当者 (複数可)
  position            : { x, y }      (親の座標系での位置)
  collapsed           : true なら下の階層を畳んで 1 枚のブロックとして表示
  artifact_ids[]      : 紐づく成果物

Port (入出力)
  id
  block_id            : 所属ブロック (最上位の入力 / 出力ノードは project 直下の特別なブロック)
  direction           : "in" | "out"
  name, description   : 形式・制約など (他人や AI が読んでも分かる書き方を促す)
  required            : 入力の必須フラグ (出力は常に必須)
  artifact_ids[]      : このポートに紐づく入力物 / 成果物
  promoted_from       : 下の階層の未接続入力を自動で引き上げた場合、元のポート id (F-06)

Edge (結線)
  id
  from_port_id        : 出力側
  to_port_id          : 入力側
  kind                : "sibling" | "up" (子の出力 -> 親の出力) | "down" (親の入力 -> 子の入力) | "auto" (F-06)

Artifact (成果物・入力物)
  id, title, url, kind ("url" | "file" | "note" | "redmine_issue" ...), note
```

結線のルール (検証ロジック。純粋関数として実装し単体テストする)
- 出力ポートからは、同じ階層のブロックの入力、または親ブロックの出力にしかつなげない
- 入力ポートには、同じ階層のブロックの出力、または親ブロックの入力からしかつなげない
- 入力ポートに来る線は 1 本まで (出力は複数に分岐してよい)。最終出力ノードは複数の入力ポートを持つことで多入力を表す
- 循環 (A -> B -> A) は禁止し、結線時にエラー表示する

浮いている入力の自動引き上げ (F-06)
- 下の階層の入力ポートが未接続なら、親に同名の入力ポートを自動生成 (promoted_from を設定) し、最上位の入力ノードまで繰り返す
- 途中の階層で別ブロックの出力につなぎ直したら、その先の自動生成ポートは消す
- 自動生成ポートと線は点線で描き、手動のものと区別する

状態の扱い
- 状態の変更は人間が明示的に行う (自動完了にはしない)
- 「下の階層が全部 White で、出力に成果物が付いている」ブロックには「完了にできます」のバッジを出す
- 下の階層を作った時点で Black -> Gray を提案する (ワンクリックで承認)

### 3.2 画面構成

```
+------------------------------------------------------------------+
| ヘッダー: プロジェクト名 / パンくず (階層の位置) / 検索 / 共有 / テーマ切替 |
+----------+-----------------------------------------+-------------+
| 左パネル | キャンバス (React Flow)                   | 右パネル     |
| ・階層の | ・ブロック (ボックスの見た目 = 状態、アバター = 担当) | ・選択した   |
|   ツリー | ・入力ノード (左端) / 出力ノード (右端)     |   ブロック   |
| ・担当者 | ・折りたたみ / 展開 (ダブルクリック)        |   の詳細     |
| ・フィル | ・階層に潜る (ズームイン) / パンくずで戻る   | ・成果物     |
|   タ    | ・ミニマップ / ズーム                      | ・AI 用      |
|          |                                         |   テキスト   |
+----------+-----------------------------------------+-------------+
| フッター: 完了率 (White 率) / 保存状態 / 書き出し / 編集中の人 (段階 2)  |
+------------------------------------------------------------------+
```

- テーマ: `prefers-color-scheme` 追従 + 手動切替 (localStorage に記憶)
- スマホ: 閲覧と状態変更はできるようにする。図の編集は PC 前提でよい

### 3.3 AI 連携 (F-17)

- 右パネルに「AI に渡すテキストをコピー」ボタン。選択ブロックを中心に Markdown で出力する
  (目的、入力・出力の名前と説明と URL、上の階層での位置づけ、兄弟ブロックとの関係)
- 定型プロンプト: 「この出力を得る手順を提案して」「このブロックを下の階層に分解して (JSON で)」
- AI が返した分解案 JSON を読み込み、下の階層のブロックとして追加する「インポート」
- 段階 3: API を MCP サーバーとして公開し、Claude Code / Codex から直接ブロックを読み書きできるようにする

## 4. 段階的な進め方

### 段階 1: 1 人用の静的アプリ (目安 2〜3 週間) -> www.sukimalog.com/apps/<名前>/

1. 新しいリポジトリ (例: ~/src/<名前>) を作成。Vite + React + TS + Tailwind + React Flow。`base` はビルド設定で切替可能にする
2. データモデルと検証ロジック (結線ルール・循環検出・自動引き上げ) を純粋関数で実装し、Vitest で単体テスト
3. キャンバス: ブロックの追加・移動・結線・折りたたみ・階層への潜り込み・ボックスの見た目による状態表示
4. 右パネル: 状態・担当者 (段階 1 はローカルの名前リスト)・成果物 URL の編集
5. 保存: IndexedDB に自動保存。JSON 書き出し / 読み込み。Markdown (AI 用) 書き出し
6. テーマ切替、キーボード操作、スマホでの閲覧
7. 配置スクリプト (File Manager API): ビルド成果物を `/apps/<名前>/` に置き、古い資産を消す。
   index.html のキャッシュが最大 1 時間残ることを踏まえ、資産はハッシュ付きファイル名にする
8. 紹介記事を /blog-post の手順で執筆。記事内に iframe の体験版 (サンプル JSON を読み込んだ読み取り専用、記事の枠に収まる高さ) と
   「全画面で開く」ボタン。アプリ側の index.html に title / description / OGP を入れ、記事からの導線で検索に載せる

### 段階 2: 招待制の共同作業 (目安 3〜4 週間) -> app.sukimalog.com

1. お名前.com で `app` の CNAME を Pages に向ける。Pages プロジェクトを作り、同じビルドを配置。旧 URL に転送用 HTML を置く
2. Hono + D1 で API: プロジェクトの作成・読込・保存 (版番号の楽観ロック)、メンバー、招待
3. ログイン: Google / GitHub の OAuth。セッションは同一オリジンの Cookie
4. 「編集中: <誰>」の軽いロック、保存の衝突時の比較画面
5. 担当者を実際のユーザーに紐づける。R2 に JSON スナップショットを日次保存 (バックアップと履歴)

### 段階 3: 世界公開と外部連携 (段階 2 の後に再見積もり)

- 公開範囲 `public`: 公開プロジェクトの一覧ページ (検索の入口にもなる)。閲覧は誰でも、提案はログインユーザー
- 提案の仕組み: ブロックに対する「解決案 (成果物の URL + 説明)」「分解案 (下の階層の JSON)」を提案として投稿し、
  owner が採用すると反映される (プルリクエストに近い流れ)。入出力の説明欄だけで協業できるよう、ポートの説明の書き方をガイドする
- 荒らし対策: Turnstile、通報、ライセンス表示 (提案物の扱い)
- Redmine 連携: Artifact の kind = redmine_issue。REST API からチケットの状態を取り込み、White 化の判断材料にする
- MCP サーバー: AI エージェントがブロックを読み書きできる API
